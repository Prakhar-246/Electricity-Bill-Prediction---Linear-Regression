# Electricity Bill Predictor

A React + FastAPI app wrapped around the **existing, unmodified** Linear
Regression model and StandardScaler from `Electricity.ipynb`
(`electricity_bill_linear.pkl`, `electricity_bill_scaler.pkl`).

## How the feature order was determined

`Electricity.ipynb`'s later cells were re-run out of order in the original
notebook (e.g. `X_train`/`train_test_split` appear used before they're
defined; `df_clean` is built before `MotorPump` is dropped and before the
`bool → int` cast). Re-implementing the notebook's *code path* wouldn't
reliably reproduce the exact 58-column order the model was actually fit on.

Instead, `backend/app/model/feature_schema.py` was generated by loading the
`.pkl` files directly and reading `scaler.feature_names_in_` — scikit-learn
stores the exact fitted column order on the object itself. That's ground
truth, independent of notebook cell order. It was then verified
programmatically:

```python
from feature_schema import ORDERED_FEATURES
assert ORDERED_FEATURES == list(scaler.feature_names_in_)  # True
```

The 58 features, in order: 10 numeric/engineered
(`Fan, Refrigerator, AirConditioner, Television, Monitor, Month,
MonthlyHours, TariffRate, HeavyAppliances, TotalAppliances_Usage`),
15 `City_*` one-hot dummies (16 cities, `Ahmedabad` dropped as baseline),
31 `Company_*` one-hot dummies (32 companies, `Adani Power Ltd.` dropped as
baseline), 2 `Season_*` dummies (3 seasons, `Post Winter` dropped as
baseline). `pd.get_dummies(..., drop_first=True)` drops whichever category
is alphabetically first, which is how the baselines above were identified.

**One deliberate, flagged simplification:** the notebook computed
`TotalAppliances_Usage` while `MotorPump` was still a column, then dropped
`MotorPump` before the final fit. The model itself has no `MotorPump`
feature. Every row in the training data had `MotorPump == 0`, so the app
doesn't expose it as a user input and computes `TotalAppliances_Usage` as if
it's always 0 — which exactly reproduces training-time values. If
`MotorPump` is meant to matter in production, that's a retraining decision,
not something preprocessing can fix.

**One dependency pin:** `requirements.txt` pins
`scikit-learn==1.6.1` because that's the version the `.pkl` files were
fitted with (visible in `InconsistentVersionWarning` when loaded with a
newer version). Predictions still work across versions here, but pinning
avoids relying on that.

Correctness check performed: the app's `/predict` endpoint was fed the
exact first row from the notebook's own training data
(Fan=16, Refrigerator=23, AC=2, TV=6, Monitor=1, Month=10, MonthlyHours=384,
TariffRate=8.4, City=Hyderabad, Company=Tata Power Company Ltd.) and returned
**3230.67**, versus the notebook's actual value of **3225.6** for that same
row — consistent with the model's own training residuals, confirming the
reconstructed pipeline matches.

Nothing about the model's coefficients, the scaler's fitted mean/scale, or
the feature engineering logic was changed. If you *want* to change any of
that (e.g. actually model `MotorPump`), it requires retraining in the
notebook, not a change here.

## Project layout

```
backend/
  app/
    main.py                  FastAPI app (/predict, /options, /health)
    schemas.py                Pydantic request/response models
    model/
      feature_schema.py       Ground-truth 58-feature order + categories
      preprocessing.py        Feature engineering + one-hot encoding
      model_loader.py         Loads .pkl files, validates schema at startup
      electricity_bill_linear.pkl
      electricity_bill_scaler.pkl
  requirements.txt
frontend/
  src/App.jsx                 Form UI, calls the API
  src/index.css
  package.json
```

## Running it

### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Visit `http://127.0.0.1:8000/docs` for interactive API docs.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Visit `http://127.0.0.1:5173`. It talks to the backend at
`http://127.0.0.1:8000` by default; override with a `.env` file containing
`VITE_API_BASE_URL=http://your-backend-host:port`.

### API

`POST /predict`

```json
{
  "fan": 16, "refrigerator": 23, "air_conditioner": 2, "television": 6,
  "monitor": 1, "month": 10, "monthly_hours": 384, "tariff_rate": 8.4,
  "city": "Hyderabad", "company": "Tata Power Company Ltd."
}
```

`GET /options` returns the exact lists of cities/companies the model was
trained on (used to populate the frontend's dropdowns, so users can't submit
an unseen category that would silently fall back to the encoding baseline).
